## Verdict

The design core is sound: transactional outbox, late-ack Celery, guarded state machine, step-level audit trail, clean connector and trigger abstractions, correct HMAC verification where it is enabled. The code is readable and mostly consistent.

The application is **not safe to expose beyond a developer machine**, and **a fresh clone probably does not run**:

- one blocker on a fresh database (F-01) and one on the frontend build (F-24);
- three critical security gaps that combine into unauthenticated remote code execution and secret disclosure (F-02, F-03, F-04);
- the reliability story in `docs/reliability.md` is only partly true in the running system (F-07, F-08, F-16);
- the test suite does not exercise any of the code that matters most.

## Findings

Severity: **Blocker** (does not work), **Critical** (compromise or data loss), **High**, **Medium**, **Low**. Effort: S under half a day, M 1-2 days, L about a week.

### Blockers

**F-01. Fresh database lacks the `request_id` columns.** `infrastructure/postgres/init.sql` has no `request_id` on `workflow_instances`, `workflow_step_executions` or `outbox`. Migration `001_add_request_id_tracing.sql` adds them but nothing applies it. The code writes them: `src/api/repository.py:61-66`, `src/orchestration/adapters/postgres_unit_of_work.py:80-117`, and reads them in `src/relay/service.py:20-22`. Effect on a new volume: starting any workflow fails, the relay errors on every poll. **Confirmed by running it:** against a database freshly built from `init.sql`, `INSERT INTO workflow_instances (..., request_id)` fails with `column "request_id" of relation "workflow_instances" does not exist`, and the relay's `SELECT ... request_id FROM outbox` fails with `column "request_id" does not exist`. Fix: add the columns to `init.sql` now (S), adopt a migration tool next (M). See ADR 0014. **Status: fixed on branch `phase-0-fresh-clone` (2026-10-10).** The columns and indexes are in `init.sql`; the same INSERT and SELECT succeed against a freshly built database.

**F-24. The frontend does not build from a clean clone.** `frontend/src/components/WorkflowGraph.tsx:2` imports `../lib/graph-layout`. The file is not on disk and was never committed, because root `.gitignore:17` (`lib/`) also matches `frontend/src/lib/`. `tsc -b` and the Docker build fail. Fix: restore the file from wherever it exists (it was presumably only on the author's machine), commit it, and change the ignore rule to `/lib/` (S). I cannot recreate the original; if it is lost it can be rewritten on top of `dagre` (S-M). **Status: fixed on `phase-0-fresh-clone`.** The original could not be recovered, so `frontend/src/lib/graph-layout.ts` was rewritten against what `WorkflowGraph.tsx` expects (top-to-bottom `dagre` layout), and `.gitignore` now anchors `/lib/` and `/lib64/`. `eslint`, `tsc -b` and `vite build` pass, the Docker image builds, and the graph renders in the running UI (7 nodes for the seed workflow, `true`/`false` labels, even 20px margins). If you still have the original file it can replace the rewrite.

**F-32. Celery cannot start on the pinned RabbitMQ 4 image.** Found on 2026-10-10 by running the stack. `docker-compose.yml` uses `rabbitmq:4-alpine` (resolved to 4.3.6) with Celery 5.5.3 / kombu 5.5.4 from `poetry.lock`. Celery declares transient, non-exclusive queues for worker remote control, which RabbitMQ 4 rejects by default (`Queue.declare: (541) INTERNAL_ERROR - Feature transient_nonexcl_queues is deprecated`). The `engine` and both `worker` containers crash-loop with `RestartFreqExceeded`, so no job is ever consumed, and `/health` is permanently 503. Together with F-01 a fresh `docker compose up` produced a stack that could not run a workflow. **Status: stopgap applied on `phase-0-fresh-clone`:** `infrastructure/rabbitmq/celery-compat.conf` sets `deprecated_features.permit.transient_nonexcl_queues = true` and is mounted into the broker. RabbitMQ will remove the feature in a future major version regardless of configuration, so this only buys time; the lasting fixes are to disable Celery remote control or to drop Celery (ADR 0017). See ADR 0003.

### Critical

**F-02. The `python_execute` sandbox does not contain user code.** `src/worker/handlers/python_executor.py` removes some builtins and restricts imports to `math json re datetime`, but running the real handler showed the import restriction can be bypassed and arbitrary modules reached; the harmless probe returned the worker's own process id. Treat every workflow author as able to run arbitrary code in the worker, which holds `DATABASE_URL`, `RABBITMQ_URL`, `REDIS_URL` and network access to the datastores. The timeout also cannot stop a runaway thread. Mechanism details are deliberately not recorded. Fix: disable by default behind a flag until replaced (S); then remove it, switch to an expression language, or move to an out-of-process sandbox without secrets or network (M-L). See ADR 0010. **Status: fixed on `phase-1-security` (2026-10-10).** The step was removed (ADR 0019); the seeded workflow now branches on `order.quantity`.

**F-03. No authentication or authorisation on any endpoint.** Everything is open: workflow create and run, instance cancel, `/admin/recover`, `/metrics`, `/health`, and `GET /connections/{id}`, which returns stored credentials in plaintext (`src/api/repository.py:164-169`, `src/api/service.py:311`). `docker-compose.yml` publishes the API on 8000, the UI on 3000, and the nginx proxy forwards all of `/api/` (F-25). Combined with F-02 this is unauthenticated remote code execution. Fix: an auth dependency on all routers except health and signed webhooks (API key or JWT/OIDC), write-only and masked secrets, `/admin` and `/metrics` internal only (M).

**F-04. Webhook verification fails open.** `src/api/trigger_handlers/github.py:20-22` and `slack.py:26-28` accept requests when the secret is unset, and `docker-compose.yml` defaults both secrets to empty. Trello is never verified (`trello.py:11-14`), and `POST /webhooks/{workflow_name}` and `/workflows/{name}/run` have no check at all. Fix: refuse to start, or reject requests, when a provider's secret is missing; verify Trello's HMAC header; give generic webhooks a per-workflow token (S-M). **Status: fixed on `phase-1-security` (2026-10-10)** for GitHub, Slack and Trello (fail closed, Trello signature verification, Slack handshake only after verification); the generic webhook and `/run` routes are covered by the API key (F-03). Per-workflow tokens are not implemented.

### High

**F-05. SQL assembled from template values.** `resolve_config` substitutes `{{...}}` into every string, including `query` in `src/worker/handlers/postgresql.py`. Trigger data (an issue title, a Slack message) can therefore alter the SQL. Fix: never template `query`; pass values only through `params` (S).

**F-06. Server-side request forgery and arbitrary datastore access.** `http_request`, `send_webhook`, Slack `webhook_url` and Postgres `connection_string` take any target from workflow config and run inside the Docker network, so they can reach RabbitMQ's management port, Redis, Postgres and cloud metadata addresses, and the response is stored in instance data and served by the API. Fix: egress allowlist or block private and link-local ranges, cap response size, and do not echo bodies back by default (M).

**F-07. The recovery sweeper is not running, and is unsafe when it does.** No `beat` service exists in compose. If started, it completes `delay` steps longer than 60 s early, re-dispatches `wait_for_event` steps as nonexistent actions, duplicates any action running over 60 s, and re-enqueues the same instance every 30 s because it never refreshes `updated_at`. `POST /admin/recover?stale_seconds=0` re-dispatches every active instance. See ADR 0007. Fix: per-step deadline events or a corrected sweeper that understands step types, plus a `beat` service (M).

**F-08. Failure paths strand instances.** (a) `WorkerService.execute_action` raises `Reject(requeue=False)` for a missing handler or instance (`src/worker/service.py:41,58`) without emitting `STEP_FAILED`, so the instance stays `running` forever. (b) An exhausted Celery retry (lock contention 12 times, other errors 3 times) fails the task and the message is acknowledged, not dead-lettered, contrary to `docs/reliability.md`. (c) The DLQs have no consumer or alert. Fix: always emit `STEP_FAILED` from the worker; on engine retry exhaustion mark the instance failed or send it to a DLQ you monitor; alert on DLQ depth (M).

**F-09. Template placeholders are not resolved in the core handlers.** `log`, `transform_data`, `http_request` and `send_webhook` (`src/worker/handlers/action_handlers.py`) never call `resolve_config`, so the seed workflow's and README's `{{priority}}` strings are logged literally and HTTP URLs or bodies with placeholders are sent as-is. Fix: resolve once centrally in `WorkerService` (except SQL, see F-05) and add a test (S).

**F-10. Workflow definitions are barely validated.** `ConnectorRegistry.validate_definition` only checks that action ids exist (`src/shared/connectors/registry.py:26-36`), and skips steps without an `action_id`. Missing: `start_at` and every `next` / `on_true` / `on_false` target exists, reachability, cycles (a branch cycle recurses until `RecursionError`, a plain loop never ends), known step types, required config, `connector_id` agrees with `action_id`, `flow_control` ids not used as actions. A dangling target raises `AttributeError` in the engine, retried then dropped (F-08). Fix: a real validator with unit tests, and a step-count guard per instance (M).

**F-11. The test suite is partly broken and misses the core.** `tests/unit/test_api_service.py` (17 tests) and `tests/unit/test_exceptions.py` (8) import `src.api.application.service` and `src.api.domain.exceptions`, deleted in the last refactor, so `pytest` stops with collection errors; the other 49 tests pass. There are no tests for the orchestrator, relay, worker service, python executor, trigger handlers (including HMAC), routers, or any integration path, and no CI configuration (`.github/` is absent). The listed `ruff` and `black` are not dependencies. Fix: repair imports (S), add orchestrator and worker unit tests plus an end-to-end test that runs the seed workflow in compose (M), add CI (S). **Status: partly fixed on `phase-0-fresh-clone`.** The two stale modules now target the refactored service (the setup patches `db_cursor` and `WorkflowRepository`; no assertion was weakened), and all 74 tests pass on Python 3.12 with the locked dependencies. `scripts/smoke.sh` runs the seed workflow down both branches against the real stack, and `.github/workflows/ci.yml` runs the unit tests, the frontend lint and build, and that smoke test (the workflow file has not run on GitHub yet). Still missing: tests for the orchestrator, relay, worker service, Python executor, trigger handlers and routers.

**F-12. Infrastructure is exposed and under-configured.** `docker-compose.yml` publishes RabbitMQ 5672 and 15672 (default `guest/guest`) and Redis 6379 (no password) to the host; Postgres credentials are `user/password`; `docker-compose.override.yml` is loaded automatically and adds `adminer` on 8080 and `--reload`; no healthchecks or restart policies on application containers; `engine`, `worker` and `relay` do not wait for Postgres. The `Makefile` used space-indented recipes, which GNU make rejects (an earlier version of this text also blamed CRLF; the repository stores LF, and only a Windows working copy gets CRLF). Fix: drop host port mappings for broker and cache (or bind to 127.0.0.1), set secrets from the environment, move adminer behind a profile, add healthchecks and `restart: unless-stopped`, fix the Makefile (S-M). **Status: the Makefile is fixed on `phase-0-fresh-clone`** (tabs, `docker compose`, a working `test`, `lint` and `smoke`; `make` itself is not installed on the machine used, so the recipes were checked structurally, not run) and `.gitattributes` keeps it LF. The rest is still open.

### Medium

**F-13. The relay will not meet the stated 2 s / 1,000 jobs/s targets.** `POLL_INTERVAL_SECONDS = 1.0` when idle (`src/relay/entrypoint/main.py:11`); each action step is two relay hops, so expect roughly 0.5 s average and 1 s worst-case delay per hop. `init.sql:66` indexes `(processed_at)` where the query sorts and filters by `publish_at`; processed rows are never purged; unmapped rows are re-selected forever; publishing uses no confirms; `RELAY_BATCH_SIZE` and `RELAY_POLL_INTERVAL_MS` from the docs do not exist. In the real stack on 2026-10-10 the seed workflow (4 trivial steps) took about 6 s from start to completion. No benchmark exists, so throughput is unproven. Fix: `LISTEN/NOTIFY` wake-up plus short poll, index on `(publish_at) WHERE processed_at IS NULL`, a purge job, env-configurable batch and interval, mark unroutable rows failed, then load test (M).

**F-14. Database connection budget is unmanaged.** Each process opens a pool of 5 to 20 connections (`src/shared/db.py:11-19`); with 4 gunicorn workers, an engine, two action workers and a relay, plus Celery's default concurrency (one child per CPU), idle connections alone can exceed Postgres's default 100 (for example 8 CPUs: roughly 145). Fix: set `--concurrency`, lower `minconn`, add PgBouncer or raise `max_connections`, set `statement_timeout` (S-M).

**F-15. Observability is largely non-functional.** Engine and worker metrics are recorded in processes that serve nothing, so `workflow_*` and `step_*` series are always empty at the API's `/metrics`; gunicorn runs four workers without multiprocess mode; `endpoint` label uses raw paths with UUIDs (`src/api/main.py:44-54`); `active_workflows` and `celery_queue_depth` are never set; `request_id` is lost after the first action (`src/worker/service.py:72-75` omits it); no `X-Request-ID` response header. `/health` also reports healthy with the relay stopped (verified on 2026-10-10: instances stayed `pending` while `/health` returned 200), because it checks neither the relay nor the outbox backlog. Fix: expose metrics from each process (or use a pushgateway or multiprocess dir), label with the route template, set the gauges, propagate the id everywhere (M). See ADR 0013.

**F-16. Duplicate-execution window and long-held transactions in the worker.** The idempotency check reads a `completed` status that only the engine sets later, so a redelivered action runs the handler again until the result is processed; the step is never marked `running`; the handler runs inside an open DB transaction (up to 300 s). Fix: claim the step atomically before running, commit before calling the handler, and use provider idempotency keys where available (M). See ADR 0006.

**F-17. Cancel can be overwritten.** `cancel_instance` writes `status` without the instance lock or a row lock (`src/api/service.py:148-161`); the engine then saves the whole instance row from its earlier read and can undo the cancel. Running actions are not interrupted. Fix: `SELECT ... FOR UPDATE` in the engine transaction and in cancel, or a version column (S-M). See ADR 0005.

**F-18. Webhook redeliveries create duplicate instances, and one route blocks the loop.** No dedupe by GitHub delivery id or Slack event id; `trigger_webhook_external` is `async def` calling synchronous database code (`src/api/routers/triggers.py:34`). Fix: store provider delivery ids with a unique constraint; make the route `def` or acknowledge first and process via the outbox (S-M).

**F-19. Secrets and large payloads spread across storage and logs.** Each step stores the full instance data as `input_data` and as `output_data` (growth is quadratic in step count, and secrets returned by earlier steps are copied); `LogHandler` logs all workflow data at INFO (`action_handlers.py:32`); `GET /instances/{id}` returns `SELECT *`; the builder keeps inline tokens in definitions after a connection is selected and shows definitions as JSON. Fix: store only deltas, redact known secret keys, cap sizes, strip credential keys when a connection is chosen (M).

**F-25. nginx exposes the whole API and sends no security headers.** `frontend/nginx.conf` proxies every `/api/*` path (admin, metrics, connections), has no CSP, `X-Frame-Options`, `nosniff` or `Referrer-Policy`, no `X-Forwarded-*`, and resolves `api` only at startup. Fix: allowlist the routes the UI needs, add headers, use `nginx-unprivileged` (S).

**F-26. Frontend error handling hides real errors.** `frontend/src/api.ts`: `get()` ignores the error body, and the other helpers read only `detail`, so backend `{"validation_errors": [...]}` (HTTP 400) shows as "400 Bad Request" and 422 array details show as "[object Object]". Fix: one shared error parser (S).

**F-27. Polling is not race-safe.** `frontend/src/hooks/usePolling.ts` has no stale-response guard or in-flight check, never resets `loading` when the fetcher changes, and one failed poll replaces the page with an error. Fix: abort and sequence requests, keep last good data on error (S).

**F-28. The builder allows invalid or silently altered workflows.** Steps can be saved with empty connector and action ids; reordering or inserting steps does not relink `next`; renaming a step remounts its editor and drops focus; a step can be named `end`; `inputs` are advisory and enforced only in the run dialog. Fix: client and server validation, stable keys, commit renames on blur (M).

### Low

**F-20. API hygiene.** Duplicate detection by matching the text "unique" in exceptions (`src/api/service.py:47,300,327`); `create_version` race on `max(version)+1` surfaces as HTTP 500; `limit`, `offset`, `status` unvalidated; CORS hard-coded to `localhost:5173` (`src/api/main.py:16-21`); `/health` triggers a Celery inspect broadcast per call; `datetime.utcnow()` is deprecated; no request size limits.

**F-21. Dependency and build hygiene.** All dependencies are `*` in `pyproject.toml` (the lock file pins builds, but any update can jump majors); `pika` and `boto3` unused; `ruff` and `black` used but undeclared; no pytest config; `celery[redis]` extra with a RabbitMQ broker; result backend hard-coded to `redis://redis:6379/1` and unused; Dockerfile default `CMD` is a no-op; the `[tool.poetry] packages` list names packages that do not exist at that path.

**F-22. Documentation drift.** README: lists an `engine/` directory that does not exist, advertises a drag-and-drop builder that does not exist, and says schema changes need `down -v`. `docs/reliability.md`: DLQ and idempotency claims (F-08, F-16), a sweeper "every 30 seconds" that is not deployed, "exponential backoff" where the code uses fixed countdowns. `docs/scalability.md`: `asyncpg`, PgBouncer, gevent workers, `RELAY_*` settings and an `outbox(publish_at)` index that do not exist. `docs/architecture.md`: handler lookup by `(connector_id, action_id)` (it is by `action_id` only).

**F-23. Dead code and layering.** `src/orchestration/adapters/postgres_lock.py`, `initial_step` and `final_step` handlers, unused gauges, an extra `find_instance` per step for metrics, the engine importing `src.api.service`, `.vscode/settings.json` committed.

**F-29. Frontend quality gaps.** No tests, no ErrorBoundary or catch-all route, almost no `aria-` or label bindings, untouched Vite README, un-typed ESLint.

**F-30. Frontend dependencies.** A delegated `npm audit` reported 18 vulnerabilities (13 high), direct ones in `react-router` and `vite`, the rest transitive. Upgrade and re-run; exploitability for this app was not assessed.

**F-31. Other frontend defects.** Edit mode shows a blank, unsaveable form when no version is active; path segments are not URL-encoded (`api.ts`); `<a href="/connections">` inside the builder discards the unsaved draft; connection form errors are not visible; object editor in `SchemaForm` has input handling bugs.

## What is good

- The outbox plus late-ack combination is correctly implemented and is the right foundation.
- State-machine guards (terminal, pending, stale step) make the engine tolerant of duplicates.
- GitHub and Slack signature checks use the raw body, constant-time comparison, and replay protection for Slack.
- Immutable workflow versions with instances pinned to a version.
- Connector catalogue drives the UI, so new connectors rarely need frontend work.
- Structured JSON logs with consistent context keys; non-root container user; multi-stage builds.
- React code has no raw HTML injection and keeps no secrets in browser storage.

## Update 2026-10-10: simplification proposal

Review of the architecture found that most of the reliability and operations findings (F-07, F-08, F-13, F-16, F-17, and parts of F-14, F-15 and F-19) come from the broker-based plumbing rather than from the product itself. [ADR 0017](adr/0017-postgres-backed-job-queue-replaces-outbox-broker-and-celery.md) and [ADR 0018](adr/0018-one-job-per-step-with-lease-fencing-and-single-transaction-advance.md) propose replacing it with a Postgres job table and one job per step, and [`spikes/pg-queue/`](../spikes/pg-queue/README.md) is a working proof (20 passing tests, real handlers, PostgreSQL 17).

If those ADRs are accepted, change the roadmap above as follows:

- Do Phase 0 and Phase 1 as written. They are independent of the runtime.
- Skip the Phase 2 and Phase 3 repairs to the current plumbing: items 10, 12 and 13, the relay parts of item 15, and the broker and metrics parts of items 16 and 17. The new design covers them.
- Keep, and still do: item 11 (definition validator and step cap), the handler security fixes (F-02, F-05, F-06), item 18 (migration tool), items 19 to 20, and everything in Phase 4.
- Before accepting, answer one question: is 1,000 jobs/s a real requirement? The unoptimised spike measured 41 to 250 steps/s on a laptop (see the spike README), so the target would need optimisation work or a different choice.
